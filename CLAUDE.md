## Working on this repo

- Sibling project: ISPy (`chaffed/luci-app-ispy`). Its CLAUDE.md has the LuCI and GL.iNet admin-panel rules this app follows; read it before touching the web UI or the GL panel.
- The results are meant to stand up as evidence for the ISP. A reading that failed (modem unreachable, login refused) is stored as *failed* with its reason, never as an empty or healthy reading.
- Run `python3 tests/backend.test.py` after touching the backend (`luci-app-modemhealth/root/usr/bin/modemhealth`). It runs the real backend in an OpenWrt 23.05 container (needs Docker) against `tests/fake_modem.py`, which replays the captured S34 replies in `tests/fixtures/s34/` and checks every signature. Test output goes to `.test-out/` because Docker Desktop on macOS doesn't share the system temp folder.
- SURFboard S33/S34 login (from the modem's own JavaScript): HNAP over JSON, HMAC-SHA256, uppercase hex. Login step 2 is signed with the *new* PrivateKey (the page stores it before sending), not with `withoutloginkey`. A `GetMultipleHNAPs` reply is wrapped in `GetMultipleHNAPsResponse` only when more than one action was asked for, so the backend always asks for several.
- The S34 answers HTTP 403 to any request whose `HNAP_AUTH` timestamp is lower than one it has already accepted (equal is fine). Busybox `date` has no milliseconds, so the backend takes real milliseconds from `ucode`'s `clock()` and never sends a timestamp below the last one (kept in `/var/run/modemhealth/last_ms`). The fake modem enforces the same rule.
- Every login adds an entry to the modem's 100-entry event log, and a check currently logs in each time. Running many checks by hand pushes real events out of the modem's log; #3 (one session between checks) fixes this.
- The modem password lives only in `/etc/config/modemhealth` (mode 600). It must never reach stored files, logs, command output or the browser; the backend test checks the first three with a password full of quoting characters.
- `tools/capture.py` saves a real modem's replies. Its output contains the modem's MAC, serial and the user's public IP: redact before anything goes into `tests/fixtures/`.
- The real test rig is a GL-BE9300 (GL firmware 4.10.1, OpenWrt 23.05), `ssh openwrt`, behind a SURFboard S34.
- `htdocs/luci-static/resources/modemhealth/health.js` holds every health limit, each with its sources (`SOURCES`: `spec`, `vendor` or `judgement`). The report cites them, so a new or changed limit needs a real source or must be marked `judgement`. No official ISP page publishes signal thresholds; the widely copied "Xfinity table" is a volunteer's forum post and is not cited. Run `node tests/health.test.js` after touching it.
- The health limits are settings (`config limits 'limits'` in `/etc/config/modemhealth`, one option per bound such as `ds_power_good_min`; empty = the default). `health.applySettings` applies them; a changed limit cites the `settings` source instead of the default's, and the pages (and the report) must say which limits were changed.
- Uncorrectable error counts are reported but not judged: no published field threshold exists, and the S33/S34 doesn't report the total codewords needed for an error rate.
- Run `node tests/ui.test.js` after touching `modemhealth/common.js`, and `node tests/luci.test.js` after touching the pages, the rpcd plugin, the ACL or the menu. The LuCI test starts OpenWrt 23.05 with LuCI in a container, installs a generated history (`tests/gen.js`, also for demo screenshots) and drives Settings and the Overview in Chrome through a real login; it needs Docker, Chrome and `npm install --no-save playwright-core`. Screenshots land in `.test-out/luci/`: look at them. `MH_KEEP=1` leaves the container up (http://127.0.0.1:18480, root / luci-test) for a look by hand.
- GL.iNet admin panel (same undocumented interface as ISPy; its CLAUDE.md has the details): view shell in `htdocs/views/`, menu entry in `root/usr/share/oui/menu.d/`, label in `htdocs/i18n/`, Lua module `root/usr/lib/oui-httpd/rpc/modemhealth`, validator exemptions in `root/usr/share/gl-validator.d/modemhealth.lua`. `modemhealth/gl.js` runs the LuCI Overview in the panel with stand-ins (`view`, `rpc`, `ui.createHandlerFn`/`showModal`/`addNotification`, `uci.load`/`get`, `dom`, `L.bind`/`L.url`, `E`, `_`); a view that uses any other LuCI API needs a stand-in there. Settings in the panel is a separate form in `gl.js`: a new setting goes into `settings.js`, `gl.js` and the module's `FIELDS` (`node tests/settings.test.js` enforces it).
- The panel can give a command only arguments (its `ngx.pipe` has no input and no environment), and arguments are readable by every process. So the panel's module writes the password to UCI itself (`set_password`), and for Test connection asks the backend for a root-only file (`modemhealth test-input`), writes what was typed into it and passes its name (`modemhealth test FILE`).
- The panel writes every RPC call to the system log unless the method's name contains `get`, `load` or `check`: hence `get_status` and `get_data`. Its `$request` refuses a result that has `err_code` or `err_msg` (as `{type: 'api', message, code, ...}`) and sends an empty Lua table as `[]`.
- Run `lua tests/gl_rpc.test.lua` (Lua 5.1 with cjson; without one locally: `docker run --rm -v "$PWD":/src:ro modemhealth-test-luci lua /src/tests/gl_rpc.test.lua`) after touching the Lua module, and `node tests/gl.test.js` after touching `gl.js`, the view shell or the module. The panel test uses a stand-in panel (`tests/gl/panel.html`, `tests/gl/rpc.lua`) written from the firmware's own `oui-rpc.lua`, `oui/rpc.lua` and app bundle; if GL changes those, the stand-ins must follow. On the real router the module can be called through the panel's local path: `curl -s -H 'glinet: 1' http://127.0.0.1/rpc -d '{"jsonrpc":"2.0","id":1,"method":"call","params":["","modemhealth","get_status",{}]}'`.
- LuCI on the real router (http://192.168.8.1:8080/cgi-bin/luci) needs the owner's login: do not make a session by hand over SSH. Check the rpcd calls there with `ubus call luci.modemhealth ...` and leave the look in the browser to the owner.
- `modemhealth/report.js` builds the report for the ISP as one HTML string (no script, no outside file, charts as inline SVG): the Report page shows it in a frame and the download is the same text. Everything from the modem, the stored files or the settings goes through `esc()`. Run `node tests/report.test.js` after touching it or `common.js`; `node tests/sample-report.js` rebuilds `docs/sample-report.pdf` (look at it; `MH_EXTRA=1` and an output folder also give the HTML and a picture). The report is cautious on purpose: failed checks are unknown, never faults; outages last "at least" what the checks prove; a report with under 72 hours of checks calls itself preliminary (our own rule of thumb).
- Charts are SVG text (`common.chartSVG`), so the pages and the report share them and node can test them; `lineChart` only wraps it in an element. Text in them must go through `esc()`.
- A report can span months, so it never loads a period whole: `common.loadDigest` judges and tallies each piece and lets the channel rows go. `common.load` (whole rows, for the Overview's tables and CSV) is for days. A channel row is joined to the line-up of its own time, not the newest (a channel that lost lock reports modulation "Unknown").
- The copy on a USB drive (`export_dir`; see the comment above `mount_of` in the backend) must only ever be written to a mounted drive: `on_drive` is checked before anything is created, because an unplugged drive's mount point is a folder in the router's RAM or flash. After every check only the rows the drive does not have yet are appended to its CSV files (nothing is rewritten; a drive that was away is caught up by the next check; the drive keeps what the router has dropped). The report file (`modemhealth-report.html`: 30 days of history plus `health.js`, `common.js`, `report.js` and `root/usr/share/modemhealth/standalone.*` in one file) holds megabytes, so it is written once a day and on "Save to the drive now", not at every check. Those three modules are pasted into `<script>` elements, so they must never contain `</script` or `<!--` (`tests/report.test.js` checks).
- Outages are worked out in two places: `health.js` (`outages`, for the pages and the report) and the backend's `outages_csv` (awk, for the outages file on the drive). Both are held to `tests/fixtures/outages/`; change them together.
- "Clear history" (`modemhealth clear`) first renames the files on the drive to `…-until-<date>-<time>` and then empties the router's history.
- A ubus reply fails somewhere between 1 and 2 MB (measured on the GL-BE9300), and a check stores about 1.4 KB, so `common.load` asks for a period in pieces of 250 checks. Anything new that returns history over ubus (the report, #10) must do the same or summarise on the router.
- S34 sessions (measured 2026-11-19): a session stays valid while used and expires after 10–15 minutes idle; an expired session is answered with HTTP 404. Several sessions can be open at once (a browser on the modem's page does not end the router's session). Checks every 5 minutes therefore keep one session for good; every login still adds a log entry.
- Storage (see the comment in the backend): daily files in `readings/` and `channels/` (days before today gzipped, days past `history_days` removed), the channel line-up in `channelmap.csv`, and the modem's running error totals in `last`. The line-up file gets an entry for a channel only when that channel's position, modulation, frequency or width changes (the first check stores all of them), so readers must look up a channel's entry by time (`common.js: lineUp`). A channel that lost lock reports modulation "Unknown"; that is not stored as a change (the lock state is in every channel row), because on a failing line it happens all day. The file is tidied once a day. Channel rows store the *change* in corrected/uncorrectable errors since the previous good check; empty means unknown (first check), and after a modem restart the change is the new count.
- A modem restart is detected when its uptime is shorter than the time since the previous good check (2 minutes' grace). The scheduler waits for the router's clock to be set (NTP) before checking, and runs on the router's uptime so clock steps can't stall it.
